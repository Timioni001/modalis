# Chainlink CRE — portfolio risk monitoring

A real workflow, not a logo. On a cron schedule it reads each watched portfolio from Monad,
computes its risk state, and writes a **DON-signed risk signal** to `RiskSignalReceiver`.

```
cron trigger
   -> read portfolioState(owner)        (RebalanceExecutor, via CRE's EVM capability)
   -> read mandateOf / allocationsOf    (PortfolioMandate)
   -> read getAsset                     (AssetRegistry — decides what counts as liquid)
   -> assessRisk()                      (packages/portfolio, the same engine the app runs)
   -> runtime.report(...)               (DON consensus + signature)
   -> writeReport -> RiskSignalReceiver.onReport
   -> RiskStateUpdated / RebalanceRequired
```

## Why this is worth doing

The risk state that lands on-chain is not something Modalis' backend asserts on its own — it
carries DON consensus. That works only because the computation is deterministic: the same
`assessRisk` function, over the same contract reads, with no clocks, randomness or private data.
Every node reaches the same answer, so the signal is verifiable rather than merely reported.

## Scope: this writes a SIGNAL, and only a signal

`RiskSignalReceiver` cannot move funds. It holds no balances and has no reference to the vault or
the executor. A rebalance still requires a proposal that passes `RebalanceExecutor`'s full
validation. **Do not describe this integration as autonomous fund movement**, because it is not,
and the brief is explicit about not making that claim.

## API provenance

Every CRE binding used here was read from the installed SDK's own type definitions
(`@chainlink/cre-sdk` 1.23.0), not from memory:

| Used | Source in the SDK |
|---|---|
| `cre.handler(trigger, fn)` | `dist/sdk/workflow.d.ts` |
| `cre.capabilities.CronCapability().trigger({ schedule })` | `dist/generated-sdk/capabilities/scheduler/cron/v1/cron_sdk_gen.d.ts` |
| `new cre.capabilities.EVMClient(chainSelector)` | `dist/generated-sdk/capabilities/blockchain/evm/v1alpha/client_sdk_gen.d.ts` |
| `evm.callContract(runtime, { call: { from, to, data } })` | same file |
| `evm.writeReport(runtime, { receiver, report, gasConfig })` | same file |
| `runtime.report({ encodedPayload, encoderName, signingAlgo, hashingAlgo })` | `dist/sdk/runtime.d.ts` |
| Monad chain selectors | `SUPPORTED_CHAIN_SELECTORS` in the EVM client — `monad-testnet` `2183018362218727504`, `monad-mainnet` `8481857512324358265` |

Protobuf JSON encodes `bytes` fields as base64, so addresses, calldata and the report payload are
converted at the boundary (`hexToBase64` / `base64ToHex` in `src/abi.ts`).

## Verification status

**Verified by execution:**

- The report payload encoding is proven against the contract that consumes it.
  `contracts/test/RiskSignalReceiver.t.sol` embeds a payload generated by `encodeRiskReport` in
  `src/abi.ts` and asserts `RiskSignalReceiver.onReport` decodes every field correctly — owner,
  status, mandate version, drift, total value and reason hash. If the workflow's encoding and the
  contract's decoding drift apart, that test fails. 6/6 tests pass.
- Base64 round-tripping of the payload is asserted.
- The workflow typechecks against the real SDK types.

**Not verified here, and why:**

- The workflow has not been run through `cre workflow simulate` or deployed to a DON. That needs
  the CRE CLI (>= v1.29.0 for Monad), `cre login`, and network access to Chainlink and Monad —
  none of which this build environment has.
- `report.encoderName` / `signingAlgo` / `hashingAlgo` are CRE platform identifiers, not values
  Modalis defines. They are configuration with documented defaults; **check them against the
  current CRE docs for your target before deploying.**
- `CRE_FORWARDER_ADDRESS` must be the real forwarder for your Monad network. The deploy script
  deliberately **skips** `RiskSignalReceiver` when it is unset rather than pinning the receiver to
  `address(0)`, so a missing forwarder shows up as "not deployed" instead of as a receiver that
  silently accepts nothing.

## Running it

```bash
# 1. deploy Modalis with a real CRE forwarder so RiskSignalReceiver is created
CRE_FORWARDER_ADDRESS=0x... DEPLOYER_PRIVATE_KEY=0x... \
  forge script script/Deploy.s.sol:Deploy --rpc-url monad_testnet --broadcast

# 2. fill config.testnet.json with the printed addresses and the owners to watch

# 3. simulate, then deploy (CRE CLI >= 1.29.0)
cre login
cre workflow simulate .
cre workflow deploy .
```

`project.yaml` is generated by `cre init` and is specific to your CRE account and target, so it is
not checked in here — generate it rather than copying one.
